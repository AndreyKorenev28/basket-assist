# 0005. Стек и архитектура MVP

- **Статус:** принято (2026-10-18)
- **Дата:** 2026-10-18

## Контекст
Требования: минимальный VPS (1 ядро / 1 ГБ), один разработчик + Claude Code, VK как канал MVP, две платформы лиг с недокументированными JSON API, расписание с переносами, мультитенантность заложить сразу. Подробная схема — `docs/architecture.md`.

## Решения
1. **Python 3.13, один asyncio-процесс** (бот + планировщик + синхронизация).
2. **VK — собственный тонкий клиент на httpx**, а не vkbottle. Нужно ~8 методов (`groups.getLongPollServer`, `messages.send/edit/pin/getConversationMembers/sendMessageEventAnswer`, `users.get`) — они уже проверены в `spikes/vk-probe/probe.py`. Плюсы: меньше зависимостей и памяти, полный контроль над ошибками (909, 917, 925, 993), проще закрыть `ChannelAdapter`. Минус: свой код на ~200 строк. *Альтернатива:* vkbottle — быстрее старт, но фреймворк диктует структуру обработчиков.
3. **HTTP к лигам — httpx** (async), DTO и настройки — **pydantic / pydantic-settings**.
4. **SQLite + SQLAlchemy 2.0 + Alembic.** Путь на PostgreSQL без переписывания.
5. **Планировщик — собственный минутный тик по состоянию БД** с журналом `notification_log` (идемпотентность), а не APScheduler. Переносы матчей автоматически двигают сводки и напоминания; перезапуск безопасен.
6. **Тесты — pytest + respx** (моки httpx), контрактные тесты адаптеров на сохранённых ответах; **ruff** — линтер и форматтер.
7. **Развёртывание — systemd + venv** (без Docker: экономия памяти на 1 ГБ), бэкап SQLite по cron с шифрованием.
8. **Конфигурация MVP** — `.env` (секреты) + `config/tenant.toml` (команда, выступления, беседа, капитан; вне git).

## Последствия
- Минимум зависимостей: httpx, pydantic, pydantic-settings, sqlalchemy, aiosqlite, alembic (+ pytest, respx, ruff для разработки).
- Переход на Telegram/Max — новый модуль в `channels/`, бизнес-логика не меняется.
- Свой VK-клиент нужно покрыть тестами на образцах ответов, включая ошибки.
